# Spec 1: POI Playground Classifier (CLI) — Claude Critique (v2)

Re-reading the current `spec.md` against the v1 consolidated critique's 12 blocking items. Repository remains empty, so verification continues to target external claims and internal self-consistency rather than code.

## Verification of v1 Blocking Items

1. **Anthropic image size limit (20MB → wrong) — RESOLVED.** FR-4.2 now states "10MB" base64-encoded and "8000×8000" max dimensions; Integration Points repeats this and explicitly notes the correction. Matches the docs fetch performed during the update.
2. **`INVALID_INPUT`/`POI_NOT_FOUND` contradiction — RESOLVED.** FR-1.1 now routes empty/whitespace input directly to `INVALID_INPUT` without going through pattern classification; FR-1.2 defines coordinate range validation with out-of-range values also mapping to `INVALID_INPUT`; FR-1.3 now defines `POI_NOT_FOUND` only for a zero-result *search* (free text, or a URL/short-link whose canonicalized form is itself a search query). These three cases are now mutually exclusive and jointly cover the space — no remaining overlap.
3. **Output schema can't represent early errors — RESOLVED.** FR-5.1 now defines `resolved` as nullable with an explicit rule ("null iff input resolution itself failed") and replaces the ambiguous `error`/`error_message` pair with a single `error: {code, message} | null` object. Data Requirements' JSON shape matches.
4. **Evidence persistence conflict at `threshold > 1` — RESOLVED.** FR-6.1 now explicitly holds positive photos in memory and only writes them after the final label is confirmed positive; its own Verify line adds the exact regression case (threshold=2, 1 of 3 positive, final negative → zero files written) that would have caught the v1 bug.
5. **`--vision-model` default vs. `--help` conflict — RESOLVED.** FR-7.1 makes it a required flag with no default; FR-4.2 cross-references this. Internally consistent now — `--help` doesn't need to show a default for a flag documented as required.
6. **Photo acquisition method / gallery scrolling / dedup / exhaustion — RESOLVED, with one loose end.** FR-3.2 now specifies: prefer direct URL extraction over screenshot, dedup by normalized URL or content hash, scroll-until-cap-or-two-empty-scrolls termination, and retrieval order = gallery order. This is a large, substantive improvement. The one thing left soft is what "normalized" means for a photo URL (e.g. stripping Google's size/query parameters so two size variants of the same photo count as one) — minor enough that I'd leave it to the implementer rather than block on it, but noting it since it's the one place FR-3.2 still uses an undefined term.
7. **Confidence aggregation — RESOLVED.** FR-4.3 defines min-of-qualifying-photos for positive, `null` for negative, with a concrete numeric example in its Verify line.
8. **Structured classifier output mechanism — RESOLVED.** AR-4.2 explicitly requires Anthropic's forced tool-choice mechanism with a named JSON schema, replacing the prior vague "structured yes/no" language.
9. **Browser-session ownership — RESOLVED.** AR-1.1 now explicitly assigns ownership to `cli.py`, describes lazy creation on first need, a single context per invocation, and closure in a `finally` block. It also explicitly states the important corollary: inputs that never need free-text search, combined with an OSM hit, never create a browser at all.
10. **Overpass missing `relation`-tagged playgrounds — RESOLVED.** FR-2.1 now uses `nwr(around:...)`, which is a documented Overpass QL combinator for node+way+relation in one clause.
11. **Server vs. client timeout conflation — RESOLVED.** FR-2.3 now separately defines the Overpass server-side `[timeout:]` value and a distinct HTTP client timeout (`--osm-timeout + 5s`), with a stated rationale (let the server's own timeout fire first).
12. **Google Maps URL canonicalization — RESOLVED.** FR-1.2 now gives an explicit precedence order (place ID/data token → destination coordinates → embedded query text) and a fallback to `INVALID_INPUT` when none are extractable.

**All 12 v1 blocking items are resolved.** This is a genuinely stronger spec than v1 — the fixes are load-bearing (they change testable behavior), not cosmetic rewording.

## New Findings (v2)

### Blocking

1. **[verified] Input-resolution timeout is referenced but never defined.** FR-5.1 states `resolved` is `null` for "a `TIMEOUT` that occurs during resolution itself (e.g. a hung free-text search)" — but no FR in Feature 1 actually specifies a timeout value or mechanism for the short-link HTTP redirect or the free-text Playwright search. Feature 2 has `--osm-timeout` and Feature 3 has `--page-timeout`, but Feature 1 has neither its own timeout flag nor an explicit statement that it borrows one of the others. An implementer can't write FR-5.1's own referenced test case ("a TIMEOUT during resolution") without inventing an unspecified timeout value. Needs one sentence in FR-1.2 or AR-1.1: either add a resolution-specific timeout, or state explicitly that the short-link HTTP fetch and free-text search reuse `--page-timeout` (which would also require restating when that value gets applied — see next finding).

2. **[verified] Ordering gap: which module sets the shared browser context's default timeout, and when?** FR-3.1 says `--page-timeout` becomes the browser context's default navigation/action timeout — but that statement lives entirely inside Feature 3. AR-1.1 (Feature 1) says the free-text resolution path may create that same shared context *before* `gmaps_scraper` (Feature 3) ever runs, if OSM never gets reached or runs after. If FR-1.2's free-text search executes against a context that hasn't yet had `--page-timeout` applied (because that line of the spec is attached to FR-3.1, which hasn't executed yet), free-text resolution would silently fall back to Playwright's own default timeout (30s) instead of the configured value — a behavioral inconsistency directly caused by where the two related statements (context creation in AR-1.1, timeout configuration in FR-3.1) now live in two different Features. Fix: move the "`--page-timeout` sets the context's default timeout" rule to sit alongside context *creation* (AR-1.1), since that's the one place in the spec that owns the context's lifecycle, rather than attaching it to FR-3.1 which may run second, third, or never.

### Non-Blocking

- **[speculative] `ClassificationResult.confidence` is `float | None`, but FR-4.3's positive-path aggregation (`min()` over qualifying photos) has no defined behavior if a classifier ever returns `is_playground=True` with `confidence=None`.** Not a problem for the v1 `ClaudeVisionClassifier` (AR-4.2's forced-schema tool use makes `confidence` a required field, so `None` shouldn't occur there), but the pluggable interface (FR-4.1) explicitly exists so a *future* classifier can be swapped in — and nothing stops a future implementation from honoring `confidence: float | None`'s stated optionality. Worth a one-line rule for forward-compatibility (e.g. "any classifier must always supply a numeric confidence when `is_playground=True`"), but low urgency since it doesn't block the current implementation.
- **[speculative] FR-6.1's parenthetical "(per FR-4.3, the ones classified before the threshold was met)" is a slightly indirect way to say "only the photos held in memory from the first sentence."** Reads correctly on a careful pass, but tightening to "the photos held in memory per the previous sentence" would remove a small amount of cross-referencing friction for an implementer skimming quickly. Wording only, not a behavior change.

## External Claims Re-Verified

- **`nwr` Overpass combinator**: confirmed as a standard convenience statement covering `node`/`way`/`relation` in one clause — no change from v1's `out center;` → `out count;` verification, which remains correct.
- **Anthropic forced tool-choice (tool use)**: confirmed as the standard mechanism for schema-constrained structured output on the Messages API — AR-4.2's approach is the right one for reliable `is_playground`/`confidence` parsing.
