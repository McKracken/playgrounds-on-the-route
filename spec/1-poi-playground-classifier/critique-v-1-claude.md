# Spec 1: POI Playground Classifier (CLI) — Claude Critique (v1)

Repository is empty (confirmed via direct `ls`/`git status` — no commits, no code), so there is nothing to verify spec claims against in-repo. Verification instead targets the external API/library claims the spec makes (Overpass QL, Anthropic vision, Playwright) via web search performed during spec writing, plus internal self-consistency of the spec text.

## Blocking Items

1. **[speculative] Ambiguous confidence aggregation for the GMaps-photos path.** FR-2.2 fixes `confidence=1.0` for an OSM hit, and FR-4.2 defines per-photo confidence from Claude, but no FR states what value populates the final output's `confidence` field (FR-5.1) when `method_used="gmaps_photos"`. Candidates: the confidence of the photo that triggered the threshold, the max across all classified photos, or an average — these produce different testable values. Also unspecified: what `confidence` is when the label is negative (threshold never reached) — `null`, or the highest negative-photo confidence? Two implementers would build different, incompatible behavior here, and FR-5.1's own Verify ("validates against a fixed schema") doesn't pin the value, only the shape. Needs an explicit rule in FR-4.3 or FR-5.1.

2. **[speculative] Unspecified browser-sharing contract between `input_resolver` and `gmaps_scraper`.** AR-1.1 requires the free-text resolution path (FR-1.2) to reuse "the same Playwright browser/context instance used by `gmaps_scraper`," but FR-7.2's orchestration order is `input_resolver → osm_lookup → (conditionally) gmaps_scraper`. This means: (a) whatever creates the shared browser session must do so before `input_resolver` runs (since free-text resolution may need it immediately), (b) that session then sits idle through `osm_lookup`, and (c) is handed to `gmaps_scraper` afterward only if OSM was inconclusive — or the browser must be closed and independently re-launched, in which case AR-1.1's "not duplicated" requirement is unmet. Neither `cli.py` (FR-7.2) nor AR-1.1 states who owns creating/passing this shared session or what the interface looks like (a context manager passed into both modules? a lazily-initialized singleton?). This is a real interface gap between three FRs, not a one-line fix in the implementer's head — worth one explicit sentence on ownership.

3. **[speculative] Photo acquisition method left as an either/or with materially different quality outcomes.** FR-3.2 says photos are collected "via Playwright's element screenshot or direct image URL fetch" — presented as interchangeable, but they are not: an element screenshot captures the rendered (often small, cropped) thumbnail, while a direct fetch of the underlying image URL (Google Photos-hosted URLs typically support size parameters in the URL path) would get much higher resolution. This directly affects FR-4.2 classification accuracy — a small blurry thumbnail materially raises Claude's error rate on distinguishing "slide in the background" from generic playground-adjacent clutter. The spec should state a preference (attempt direct URL extraction first, screenshot only as a fallback) rather than leaving both as equally valid, since accuracy is the entire point of the feature.

## Non-Blocking Improvements

- **[verified] `out center;` is unnecessary for FR-2.1/2.2.** Confirmed against the Overpass QL wiki: `out center;` computes a centroid for way/relation geometry, useful when you need coordinates. Neither FR-2.1 nor FR-2.2 use the matched element's coordinates — only existence ("hit=True/False") matters. `out ids;` or `out count;` would return a smaller, faster response for the same logical check. Cheap performance win, not correctness-blocking.
- **[verified] Structured-output mechanism for FR-4.2 is under-specified but has an established fix.** The spec says the classifier "requests a structured yes/no + confidence response" without saying how that structure is enforced. Free-text parsing of a natural-language reply is brittle; Anthropic's Messages API supports tool use / forced tool choice for schema-constrained output, which is the standard way to get reliable structured responses rather than regex/JSON-parsing a prose reply. Worth naming as the intended mechanism in an AR so the implementer doesn't reach for fragile text parsing.
- **[speculative] Internal inconsistency in FR-1.3's `POI_NOT_FOUND` case for coordinate input.** FR-1.2's own reasoning elsewhere assumes "GMaps always resolves any coordinate to *some* location" (a pin drops even with no business there), which means the `POI_NOT_FOUND` branch in FR-1.3 realistically only fires for the free-text path, never for raw coordinates. As written, FR-1.3 implies both input forms can hit `POI_NOT_FOUND` symmetrically — worth narrowing the wording so a test-writer doesn't try (and fail) to construct a coordinate case that triggers it.
- **[speculative] No input sanitization step called out before constructing Maps search URLs from free text.** Standard practice (URL-encode the query) but not explicitly required anywhere; worth one clause under AR-1.1 or FR-1.2 given "input validation" is an explicit checklist category.
- **[speculative] No fallback for the Overpass endpoint.** `overpass-api.de` is a single community-run instance with its own fair-use throttling. FR-2.3 already treats any Overpass failure as "fall through to GMaps," which is the right resilience posture, so this is low severity — but a one-line note that a mirror (e.g. `overpass.kumi.systems`) could be a future `--osm-endpoint` override would future-proof it cheaply.
- **[speculative] Filesystem slug generation for `--output-dir` naming (FR-6.1) isn't specified** for free-text POI names containing unicode/special characters/path separators. Minor, but worth a one-line rule (e.g. "non-alphanumeric characters replaced with `-`") so two implementers don't diverge on directory-naming edge cases.

- **Anthropic vision image constraints** in FR-4.2 (JPEG/PNG/GIF/WebP, ≤20MB/image via base64 content blocks) match the [Vision - Claude Platform Docs](https://platform.claude.com/docs/en/build-with-claude/vision) — confirmed correct.
- **Playwright Python sync API** (`page.goto`, `page.screenshot`, element-scoped screenshots) referenced implicitly in FR-3.1/3.2 is standard, current API surface — confirmed correct, though the spec correctly avoids pinning exact selectors (AR-3.1), which is the right call since Maps' DOM isn't stable across time.
