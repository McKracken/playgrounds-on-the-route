## Blocking Items (v2)

1. **[CONFIRMED — both critiques] FR-1.3's Verify line contradicts its own rule.** It says "an empty/gibberish-but-non-coordinate-shaped input returns `INVALID_INPUT`." But per FR-1.1, non-empty gibberish is classified as free text (the catch-all), and per FR-1.3's own `POI_NOT_FOUND` rule, a zero-result free-text search returns `POI_NOT_FOUND` — not `INVALID_INPUT`. The acceptance test contradicts the behavior it's meant to verify. **Fix:** change the Verify line's gibberish example to expect `POI_NOT_FOUND` (via a mocked zero-result search), and keep a separate, actually-invalid example (empty/whitespace) for the `INVALID_INPUT` case.

2. **[CONFIRMED — Codex] Browser ownership is still asserted in two places with different models.** AR-1.1: "`cli.py` … owns creating this Playwright browser/context … passes the same context into whichever module needs it." FR-3.1: "`gmaps_scraper` launches a headless Chromium instance via Playwright (or reuses the shared context … if one already exists)" — phrasing that still allows `gmaps_scraper` to be the one launching a browser. **Fix:** reword FR-3.1 to say it *receives* the context created by `cli.py` (per AR-1.1) and never launches its own; only `cli.py` ever calls the Playwright launch/close APIs.

3. **[CONFIRMED — Codex] The Maps-URL place-ID branch isn't executable as specified.** FR-1.2's precedence order lists "an embedded place ID / data token" as the first-choice canonicalization source, but a Google place ID is an opaque textual identifier, not a lat/lng pair — resolving it into `ResolvedPOI`'s required coordinates needs *some* mechanism (an API call, or navigating the URL and reading back the page's resolved state), and none is specified. AR-1.1 further restricts browser access to "only for the free-text path," which excludes the most natural mechanism (navigate the URL via Playwright and read the result) from this branch. **Fix:** the simplest correction is to unify the mechanism — for *any* Maps URL/short-link that lacks explicit `@lat,lng` destination coordinates (whether it carries a place ID, a query string, or both), resolve it the same way free text is resolved: navigate it in the shared Playwright context and read back the coordinates from the loaded result. Only the "explicit `@lat,lng` in the URL" branch stays browser-free. This also simplifies AR-1.1, which can then say "the browser is needed whenever the input isn't a bare valid coordinate pair with no page navigation required," rather than carving out free text as a special case.

4. **[CONFIRMED — Codex, I'd under-called this as non-blocking in my own pass] `ClassificationResult.confidence: float | None` is incompatible with FR-4.3's mandatory `min()` aggregation.** If any qualifying (`is_playground=True`) photo has `confidence=None`, `min()` over the qualifying set is undefined — different implementers would handle it differently (skip it, treat as 0, crash). **Fix:** make `confidence` a required `float` in `[0, 1]` for every *successful* `ClassificationResult` (Data Requirements) — a photo that fails to classify doesn't produce a `ClassificationResult` at all; it's handled entirely by FR-4.4's skip-and-continue path. This removes the `None` case from the type actually being aggregated.

5. **[CONFIRMED — Codex] AR-7.1's exit code 2 (argparse validation failure) contradicts AR-7.2's exit-code contract.** AR-7.2 states exit code is 0 for any well-formed JSON result and 1 only for unhandled internal failure — implying those are the only two codes — while AR-7.1 requires a standard argparse rejection (exit code 2, no JSON) for invalid config. **Fix:** add one sentence to AR-7.2 explicitly carving out exit code 2 as reserved for pre-pipeline CLI usage/validation errors (argparse's own behavior, no JSON emitted, since the pipeline never started) — distinct from the 0/1 contract that applies once the pipeline actually runs.

6. **[CONFIRMED — my own re-read, not raised by Codex] FR-5.1 references a resolution-stage `TIMEOUT` that Feature 1 never defines.** FR-5.1 says `resolved` is `null` for "a `TIMEOUT` that occurs during resolution itself (e.g. a hung free-text search)," but no FR in Feature 1 specifies a timeout value or mechanism for the short-link HTTP redirect fetch or the free-text/URL-navigation Playwright search. **Fix:** once Blocking Item 3's unification lands (all non-trivial resolution paths go through the shared Playwright context), state that resolution-stage browser operations are bounded by the same context-level timeout as scraping (i.e. derived from `--page-timeout`); give the short-link HTTP redirect fetch its own small explicit timeout (e.g. a fixed few seconds, since it's a single HTTP HEAD/GET, not a full Maps page load).
