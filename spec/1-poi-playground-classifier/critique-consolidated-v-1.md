# Spec 1: Consolidated Critique (v1)

## Overview
**Critiques received from:** Claude (direct), Codex
**Critiques missing:** Gemini — the `gemini` CLI is not installed on this machine, so this round has no Gemini pass.

## Executive Summary
Both critiques agree the module split (OSM-first, Playwright/Claude fallback, pluggable classifier) is sound and implementable, but the spec has several **internal contradictions** in its output/error contract and **underspecified decision rules** that would cause two implementers to build materially different, incompatible behavior. Codex additionally caught one concrete factual error I introduced while writing the spec (Anthropic's image size limit), which I independently re-verified against the current docs and confirmed wrong as written — see Blocking Item 1. Codex's pass was significantly more exhaustive (49 numbered findings, most `[verified]` against primary docs); Claude's pass converges on a subset of the same core issues plus a couple Codex didn't raise (input-resolution/scraper browser-sharing contract, POI_NOT_FOUND asymmetry).

## Blocking Items

1. **[CONFIRMED] Anthropic image size limit is wrong.** Spec says ≤20MB/image; the actual direct-API limit is **10MB base64-encoded**, max dimension 8000×8000px, with automatic downscaling by resolution tier (I re-fetched `platform.claude.com/docs/en/build-with-claude/vision` directly and confirmed this). Also worth noting from that same fetch: sending more than 20 images in a *single request* triggers a stricter per-image dimension cap — not directly relevant since FR-4.2 classifies one photo per call, but worth stating that explicitly in the spec so a future batching optimization doesn't silently break. *(Codex #1, independently verified)*

2. **[CONFIRMED] FR-1.1 and FR-1.3 contradict each other on `INVALID_INPUT`.** FR-1.1 defines free-text as the catch-all for anything not matching URL/short-link/coordinate patterns — meaning nothing can ever fail to "match a known pattern." FR-1.3 then conditions `INVALID_INPUT` on the input "matching no known pattern," which per FR-1.1's own definition is impossible. Re-reading my own spec text confirms this is a real self-contradiction, not a nitpick — an implementer literally cannot write a test that reaches `INVALID_INPUT` via free text as currently worded. Needs a concrete rule (e.g., empty/whitespace-only input, or a free-text search returning zero results, is `INVALID_INPUT`; a *non-empty* search with a resolvable-but-wrong result, or no result at all, is `POI_NOT_FOUND`). *(Codex #2, confirmed on re-read; overlaps Claude's note on `POI_NOT_FOUND` asymmetry for coordinates)*

3. **[CONFIRMED] The output JSON schema (FR-5.1) can't represent early-pipeline errors.** `resolved`, `label`, and `method_used` are specified as always-present/typed, but `INVALID_INPUT` and `POI_NOT_FOUND` occur *before* a `ResolvedPOI` or method exists. Also, "`error` … plus a human-readable `error_message`" is ambiguous about whether `error` is a bare code string or an object containing the message. Needs an explicit success-vs-error schema split (which fields are nullable/absent on which error codes). *(Codex #3)*

4. **[CONFIRMED] Evidence persistence (FR-6.1) and negative-result cleanup (FR-6.2) conflict whenever `threshold > 1`.** FR-6.1 writes each positive photo to disk as it's found; FR-6.2 says a final negative result leaves no files. If threshold=2 and only 1 of 20 photos is positive, FR-6.1 already wrote that photo to disk before the final (negative) label is known, directly violating FR-6.2. Needs a staging rule: buffer positive photos in memory until the final decision, then persist only if the final label is positive. *(Codex #9)*

5. **[NEEDS YOUR INPUT] No executable default for `--vision-model` conflicts with FR-7.1.** This traces directly back to your choice during requirements refinement ("configurable parameter, default undecided"). FR-7.1 requires `--help` to list every flag's default, but FR-4.2 explicitly mandates no spec-level default for `--vision-model` — so a run with no flag has no model to call, and `--help` can't show a default that doesn't exist. Options: (a) make `--vision-model` a *required* flag (no default, but also not optional — argparse can enforce this), or (b) let the implementer pick and document one concrete default while keeping it overridable. I'd lean toward (a) since it matches your original intent more literally, but this is genuinely your call. *(Codex #8, but the tension originates in a decision you made, not an oversight — flagging distinctly)*

6. **[CONFIRMED] Photo byte-acquisition method is left as an interchangeable either/or, but the two options produce very different classification accuracy.** FR-3.2 says photos are collected "via Playwright's element screenshot or direct image URL fetch" as if equivalent. An element screenshot captures a small, often-cropped rendered thumbnail; a direct fetch of the underlying photo URL (if extractable from the DOM) gets much higher resolution — directly affecting how well Claude can actually spot playground equipment. Codex's independent pass goes further: gallery scrolling/lazy-loading, dedup-by-URL-or-hash, "retrieval order" (undefined), and the exhaustion condition (when has the gallery truly run out vs. just not finished loading) are all unspecified, and these interact with cost/early-stop (FR-4.3). This is the single largest scoping gap in the spec — it's the one area where "the implementer will figure it out" risks silently reimplementing the riskiest, least-specifiable part of the whole system differently than intended. *(Claude #3 + Codex #7, #28, #39 — consensus, Codex's version is more complete)*

7. **[CONFIRMED] No confidence-aggregation rule for the GMaps-photos path.** FR-2.2 fixes `confidence=1.0` for OSM; FR-4.2 gives per-photo confidence; nothing states what value lands in the final output's `confidence` field when multiple photos are classified, nor what it is on a negative result (`null`? lowest negative confidence?). *(Claude #1 + Codex #27 — consensus)*

8. **[CONFIRMED] Structured-classifier-output mechanism is unspecified.** "Structured yes/no + confidence response" doesn't say *how* that structure is obtained/enforced (free-text parsing vs. Anthropic tool-use/forced-schema output), nor the confidence scale, nor how a malformed/partial response is handled before it counts as a `CLASSIFIER_ERROR`. Recommend explicitly requiring Anthropic tool-use (forced tool choice) with a defined JSON schema rather than parsing prose. *(Claude non-blocking + Codex #25 — Codex treats this as more severe; on reflection I agree it's blocking, not a nice-to-have, since it affects testability directly)*

9. **[CONFIRMED] Browser-session ownership between `input_resolver`'s free-text path and `gmaps_scraper` is unspecified.** AR-1.1 requires reuse of "the same Playwright browser/context," but FR-7.2's orchestration order (`input_resolver → osm_lookup → gmaps_scraper`) means the shared session must be created before resolution, sit idle through the OSM step, and conditionally hand off to scraping — and nothing states who owns creating/closing it or the interface for passing it between modules. Codex's #41 adds: this means the "no browser automation" fast path only truly applies when OSM resolves an input that *didn't* need free-text search to begin with — worth stating that limitation explicitly. *(Claude #2 + Codex #41 — consensus)*

10. **[CONFIRMED] Overpass query misses relation-tagged playgrounds.** FR-2.1 queries only `node`/`way`; some playgrounds are mapped as `relation` (e.g., multipolygons). Use `nwr[...]` or add an explicit `relation` clause. *(Codex #11, verified against Overpass QL docs)*

11. **[CONFIRMED] Server vs. client timeout conflated in `--osm-timeout`.** `[timeout:{timeout}]` in the Overpass query is a *server-side* setting; the HTTP client needs its own separate connect/read timeout, or a slow socket can exceed the "10 second" bound the flag implies end-to-end. *(Codex #13)*

12. **[CONFIRMED] Google Maps URL canonicalization is underspecified.** A Maps URL can carry viewport coordinates, destination coordinates, a place ID, and free-text query all at once — the spec doesn't say which one wins or how a `ResolvedPOI` is built when multiple are present or none are extractable. This blocks writing a reliable FR-1.2 implementation/tests. *(Codex #6)*

## Ambiguities Requiring Clarification (non-blocking but worth a decision)

- **Binary label vs. an "unknown" outcome.** Both critiques independently raise that "no playground nearby" is a claim the pipeline can't actually prove — OSM absence is inconclusive by design (FR-2.3 already treats it that way), and "not shown in a POI's sampled photos" isn't the same as "doesn't exist nearby." Codex frames this as a product-semantics gap (findings #4, #5, #23): the OSM path answers "playground within 150m," the photo path answers "does the POI's own gallery show equipment," and these are two different propositions being merged into one label. Worth a deliberate decision on scope/labeling, not necessarily a spec blocker for v1 given you already accepted this as a heuristic — but should be named as a known limitation in Assumptions & Risks rather than left implicit.
- CLI numeric invariants unenforced (`threshold` vs `max_photos`, positive radii/timeouts) — Codex #20.
- Error taxonomy incomplete for realistic failure modes: missing/invalid API key, browser executable missing, disk-full on evidence write, malformed Overpass JSON, etc. — Codex #29.
- Exit codes / stdout-stderr discipline for a scriptable CLI aren't specified — Codex #32.
- Checklist self-grading was optimistic in three places: **Security review**, **Performance impact**, and **Error handling & failure modes** should move from `[x]` to `[ ]` given findings 1, 3, 4, 6, 7, 9 above and Codex's #34–37 (SSRF/redirect allowlisting if this ever becomes a service, the "no PII collected" claim being unjustified given free-text addresses/photographed faces, no overall latency/memory/cost budget across up to 20 sequential Claude calls).

## Additional Requirements Identified
- A `Photo`/stage-result value type carrying MIME type, source URL/provenance, and raw bytes together (today `PlaygroundClassifier.classify(bytes)` can't hand provenance to the evidence sidecar, which needs it) — Codex #46.
- Explicit dependency list (HTTP client, image-processing library for resize/validation, Playwright's separate browser-binary install step via Poetry) — Codex #45.

## Non-Blocking Improvements
- Use `out ids;`/`out count;` instead of `out center;` in the Overpass query — the center coordinate is never used (Claude, verified).
- Note a fallback Overpass mirror (`overpass.kumi.systems`) as a future `--osm-endpoint` override (Claude).
- URL-encode free-text input before constructing a Maps search URL (Claude).
- Slug-generation rule for `--output-dir` naming with unicode/special characters (Claude).
- Playwright's default action/navigation timeouts (30s) are independent of `--page-timeout`; if "any step" in FR-3.3 is meant literally, say so and wire the flag through explicitly rather than relying on Playwright's own defaults (Codex #16).

## Response to Spec Completeness Checklist
The spec's self-grading was reasonable in intent but too generous in three spots given the findings above — see "Ambiguities Requiring Clarification" for which items should be reopened to `[ ]` pending the blocking-item fixes.
